# The reference and the oracle — ProjectPSX with trace logging; SwanStation unmodified, recorded from outside

**What / why.** The Swift PS1 core is checked two ways ([SPEC.md](../../assistant/SPEC.md) → Porting): instruction by instruction against the permissive reference it is ported from, ProjectPSX, and by guest-visible state against the more accurate GPL oracle, SwanStation. Neither can produce a trace yet. What shapes this item, checked 2026-11-07:

- **ProjectPSX** (MIT) is a .NET 10 core library (`ProjectPSX/`) with a cross-platform OpenTK frontend; its README says a valid BIOS is required (SCPH1001 is its development default). The .NET SDK is not installed on the user's Mac. MIT allows adding trace logging to its source.
- **SwanStation** (GPLv3) may only be built unmodified from its public repository and run ([ADR 0013](../../adrs/shipped-code-derives-only-from-permissive-references.md) §2): its source is never opened. It ships as a libretro core, and the libretro API exposes guest-visible state without its internals — guest RAM through `retro_get_memory_data(RETRO_MEMORY_SYSTEM_RAM)`, each video frame through the video callback, audio through the audio callbacks, and its options through the environment calls it makes. RetroArch is not installed, so a small headless frontend of iStation's own drives it.
- **Revula** records from outside only where the libretro API is not enough — LLDB or Frida for guest state — and never disassembles or decompiles SwanStation.

**Core constraint(s).** GPL emulators are black boxes (⚠ in CLAUDE.md): SwanStation is built unmodified and only run; its options are learned from the requests it makes and libretro's public documentation, not its source; the frontend's libretro header comes from libretro's own MIT-licensed `libretro-common`, not from SwanStation's tree. A session that has read a GPL emulator's source doesn't build this. No Sony files: the user's BIOS dump is passed by path at run time and never copied into the repository — a run with it is the user's to start. Nothing here ships: both tools live under `tools/`, git-ignored builds in their `.build/`.

**Seam + files.** No module.
- `tools/projectpsx-trace/` — `README.md` (MIT, the pinned ProjectPSX commit), `build.sh` (clone at the pinned commit into `.build/`, apply the patch, build with the .NET SDK), `trace.patch` (per-instruction records in the trace format ([reference/trace-formats.md](../../reference/trace-formats.md), shipped with 3c) from ProjectPSX's CPU loop; per-frame records from its frame loop), and a small console host that runs a BIOS, or a BIOS then a PS-EXE, for a given number of frames.
- `tools/swanstation-oracle/` — `README.md` (the pinned SwanStation commit; "built unmodified, source never read"), `build.sh` (clone and build the libretro core unmodified into `.build/`), and `frontend.c` (MIT, iStation's own): loads the core, logs every option key it asks for, answers with the interpreter and a system directory holding only the BIOS the user names, runs a given number of frames, and writes per-frame records in 3c's format.
- Docs: DEVELOPER.md's tree and commands; the router's note on `tools/`.

**Reference.** ProjectPSX's own source (MIT). libretro's public API documentation and `libretro.h` from `libretro-common` (MIT). psx-spx for the guest-visible state worth recording.

- 2026-11-07 (building): `trace.patch` adds one file of iStation's own, `IStationTrace.cs` (MIT), which writes the instruction, full-state and frame records and the TTY, and hooks it into ProjectPSX with a few lines: the instruction retired at the end of `CPU.Run()`, the BIOS's putchar as ProjectPSX's `TTY()` tests it, expansion 2's DUART, a settable BIOS path, readable guest RAM, and "no disc" accepted. A frame record is written at each vertical blank, when ProjectPSX's GPU calls `Render` — the Swift console's frame boundary too (the agent's call, in the group's run).
- 2026-11-07 (building): there is never a disc, and ProjectPSX can't answer "no disc": its CD has no tracks without a disc image, so with the lid closed a BIOS's GetID or ReadN threw (found by the tools' review with images built in code). The host opens the lid instead, so a BIOS sees an open lid, not an empty closed drive, and its disc checks may take another path than on the Swift console and SwanStation — a difference to expect in 3g's ProjectPSX comparison. The host also answers ProjectPSX's waits for console input at once, checks the BIOS's size and `--exe` first, and exits 2 for wrong arguments or an output file it can't write, 3 when ProjectPSX throws while running (keeping what was recorded, naming the frame), and 4 when, with `--exe` and `--tty`, the EXE never started (the agent's call, in the group's run).
- 2026-11-07 (building): SwanStation is pinned at `631f0fb31b809e0f889d7c551fe695788e39c1d3` and `libretro.h` at libretro-common's `d9597c359a5ca8399a4e244f816e7e975a92a2aa`. The helper session cloned and built the core and relayed only commands and results; this session never opened `.build/swanstation` or `.build/build`, and `build.sh` sends the core's build output to a log file no core-writing session opens (the agent's call, in the group's run).
- 2026-11-07 (building): the core's options are learned from the requests it makes: `CPU_ExecutionMode` is answered `Interpreter`, `GPU_Renderer` `Software`, the memory cards `None`, every other option its first value, never OpenBIOS; no controller is plugged into either port. The core asks for its NTSC-U BIOS as `scph5501.bin`, so the frontend links the user's BIOS under each `.bin` name it asks for. The Swift console has no pads or cards, and one answering the BIOS would change guest RAM (the agent's call, in the group's run).
- 2026-11-07 (building): the oracle's frame records carry guest RAM's checksum; their picture and sound checksums are 0, as the trace format (3c) leaves them until v0.1.0 and v0.2.0 define them, so the per-frame comparison is RAM's until then — the image and audio in the decision above wait for those versions (the agent's call, following the format, departing from the decision above — an open call below).
- 2026-11-07 (building): with images built in code, SwanStation's TTY can't be heard. A program built in code that prints through the BIOS's putchar and through expansion 2 prints both lines on the Swift console and on ProjectPSX, while the core's log, 522 lines at every level, holds neither: the core passed no TTY to libretro's log. For this item's guardrail that is the oracle's known gap unless the user's run with a real BIOS shows otherwise (the agent's finding; 3g's expected outputs follow from it — an open call there).
- 2026-11-07 (building): no console has a pad or a memory card. The oracle plugs nothing in; `trace.patch` leaves both of ProjectPSX's slots empty, though ProjectPSX always builds a digital pad and a card; and the Swift console's controller port answers as an empty one (Milestone J), as ProjectPSX's JOYPAD does with no device and as SwanStation does with nothing plugged in once an exchange completes: a byte sent comes back 0xFF and sets JOY_STAT's RX-not-empty until read. Before, the Swift port never set that flag and ProjectPSX's pad answered with an acknowledge and its ID, so a BIOS polling the pads would have written different RAM on each (found by the second and third reviews, with images built in code that drive the port). Known differences that remain, for 3g to show if they matter: the Swift exchange is instant and needs nothing of JOY_CTRL, where SwanStation's takes time and waits for TX enable and /JOY; wider RX reads, JOY_BAUD across a reset and JOY_CTRL's bit 4 differ from SwanStation; ProjectPSX's JOY_STAT carries the baud timer in bits 11 and up (the agent's call, in the group's run).
- 2026-11-07 (building): ProjectPSX side-loads an EXE only by patching SCPH-1001's LoadRunShell at 0xBFC06FF0, so the ps1-tests runs on ProjectPSX need that dump; the Swift console starts an EXE when any BIOS reaches its shell. On both, a test's TTY starts at the EXE's entry point, leaving out the BIOS's own messages, which `psx.log` doesn't hold (the agent's call, in the group's run).
- 2026-11-07 (building): 3e's guardrail is met (Milestone I, "Trace against trace"): the CPU-check program, built in code, agrees on ProjectPSX's traced build and the Swift console for all 18,833 instructions of ProjectPSX's frame, registers and cycles — again after the review added psx-spx's division edge cases; and SwanStation's frame records on the same image match the Swift console's, identically, over 5 frames (the agent's record).
- 2026-11-07 (building): both `build.sh` scripts build from a clean checkout. ProjectPSX's, from a fresh copy of its folder, with every output — intermediates included — inside `.build/`. SwanStation's was run from a fresh copy by the helper session, which reported numbers only: exit 0 in 45 seconds with the clone, HEAD at the pin, the clone's tree unchanged, the core 4,906,856 bytes. That fresh core's frame records match the Swift console's on the CPU-check image, identically, over 5 frames (the agent's record).
- 2026-11-07 (building): an adversarial review of the tools before committing confirmed 30 defects — among them the gate stopping at its first failing tool, ProjectPSX's no-disc crash, the TTY including the BIOS's messages, the oracle's default pad and memory card, and paths resolved from the wrong folder — and all were fixed; a second pass over the fixes found 25 more — among them ProjectPSX waiting on console input, the TTY comparison failing on `psx.log`'s missing blank line and last newline, an EXE that never started passing for its BIOS's output, the Swift console's controller port, and one bad frame trace hiding the others — and a third pass 14 more — among them a reused output folder passing an earlier run's files for its own, and ProjectPSX's own pad and card — and all were fixed (the agent's record).
- 2026-11-07: the item stops at the user's runs, prepared in `tools/gate/run.sh` and each tool's README ("Your runs"): the boot on each tool, and ps1-tests' `cop` and `code-in-io` on each (`tools/ps1-tests/fetch.sh` downloads them, also the user's to start). Their results fill the acceptance criteria below, then 3d ships (the user's call, recorded above).
