# Gate: the BIOS boots — ps1-tests' CPU tests pass, and the guest-state trace matches SwanStation's

**What / why.** v0.0.1's PS1 milestone (the user's brief, 2026-11-07): the R3000A interpreter, the memory map and the BIOS boot, passing ps1-tests' CPU tests, with a guest-state trace that matches SwanStation's. ProjectPSX needs a real BIOS, and OpenBIOS is not used ([ADR 0013](../../adrs/shipped-code-derives-only-from-permissive-references.md) §6), so the gate runs in a personal build with the user's own BIOS dump — the user's run.

Checked 2026-11-07: ps1-tests (MIT) has four CPU tests — `access-time`, `code-in-io`, `cop` and `io-access-bitwidth`. `cop` and `code-in-io` report `pass - …` lines over TTY and ship a `psx.log` recorded on a real PS1 (495 and 247 bytes); the programs themselves ship only in the 2021 release `build-158` (`tests.zip`, 6.6 MB) and leave the stack pointer at 0.

**Core constraint(s).** No Sony files: the BIOS is passed by path in a personal run and never copied into the repository; ps1-tests' programs are fetched from their release into a git-ignored folder (⚠ in CLAUDE.md). GPL emulators are black boxes: the comparison uses only 3d's recorded guest state. Release builds carry no tools: the runner is personal-only.

**Seam + files.**
- A personal-build runner (in the macOS app's personal routine or a small tool beside 3d's): boots the BIOS, or the BIOS then a PS-EXE, in `BusinessPS1` with TraceKit recording, and prints the TTY.
- `tools/ps1-tests/fetch.sh`: downloads release `build-158` into a git-ignored folder, beside its MIT licence.
- `tools/gate/run.sh`: runs the boot and the four CPU tests, diffs per-frame traces against SwanStation's and per-instruction traces against ProjectPSX's (3d), compares each test's TTY with its `psx.log` where one exists, and writes a report.
- MILESTONES: the report's numbers.

**Reference.** [ps1-tests](https://github.com/JaCzekanski/ps1-tests) `cpu/` (sources and `psx.log`, MIT). the trace format ([reference/trace-formats.md](../../reference/trace-formats.md), shipped with 3c)s and diff; 3d's tools.

**Decisions made** (dated):
- 2026-11-07: the milestone is the brief's — all of ps1-tests' CPU tests and a trace matching SwanStation's — replacing Milestone C's narrower bar (the user's brief).
- 2026-11-07: OpenBIOS is not used, as a binary either, so the boot needs the user's BIOS (the default, taken; ADR 0013 §6).
- 2026-11-07: "boots" means the BIOS reaches its shell, measured as the frame where SwanStation's recorded RAM stops changing in the boot sequence's pattern for 60 frames; the gate compares every frame up to it (the default, confirmed by the user).
- 2026-11-07: for `access-time` and `io-access-bitwidth`, which ship no `psx.log`, SwanStation's TTY in 3d's run is the expected output (the default, confirmed by the user) — superseded below by the user's call of the same day.
- 2026-11-07: the gate's run with the user's BIOS is prepared with exact steps and made later (the user's call).
- 2026-11-07 (a correction of fact, found building 3f): `access-time` and `io-access-bitwidth` do ship a `psx.log` recorded on hardware. The decision above stood — SwanStation's TTY their expected output, the hardware log beside it — until the user's call below.
- 2026-11-07 (prepared in the group's run, ahead of 3d's runs; the row stays 🔒 on 3d): the runner is `tools/istation-run`, the seam's "small tool beside 3d's", which prints a run's instructions and instructions per second (the emulation's time alone) and, with an EXE, writes the TTY from the EXE's entry point on. `tools/gate/run.sh <bios> [--scph1001]` makes 3d's runs and this item's in one sitting — the boot on all three tools (1,200 frames per frame, the first 60 per instruction), the four CPU tests on each, every TTY against its `psx.log` — and writes `report.md` and `frames.tsv`, every frame's RAM checksum on all three, to find the boot's end. A tool that fails is listed at the top of the report and the gate goes on; a trace cut short never reads as agreement. `tools/ps1-tests/fetch.sh` also fetches the four `psx.log` files at `f727802fead1`, all four or none. Dry-run on the CPU-check image with stand-in tests, a broken EXE among them: every step ran, the failure was listed, and the three consoles' frame records were identical over 120 frames. An adversarial review of the gate and the tools found 30 defects before the commit, all fixed. What is left is the user's run and the report it writes (the agent's call, in the group's run; the user's call that the run is theirs, above).
- 2026-11-07 (found preparing the run): with images built in code, SwanStation's TTY can't be heard — the core passed none to libretro's log ([3d](reference-and-oracle-traces.md)'s decisions) — so the decision above that SwanStation's TTY is `access-time`'s and `io-access-bitwidth`'s expected output may not be possible to carry out as made. The user's run checks it with a real BIOS: if SwanStation is heard there, that decision stands. Until then the gate compares all four tests with their hardware `psx.log`, as text (carriage returns, the blank line before the first and a missing last newline don't count), and the report lists each difference and how many `psx.log` lines SwanStation's log holds (the agent's call; the user's answer follows).
- 2026-11-07: every CPU test's expected output is its hardware `psx.log` — `access-time`'s and `io-access-bitwidth`'s included, in place of SwanStation's TTY. A test passes when its output, compared as text, matches `psx.log` or differs only where a known gap below explains it (psx-spx's access-time formula misses expansion 2, the CD-ROM and the SPU), each such difference listed in MILESTONES; SwanStation's TTY, if the run hears it, is shown beside, as the gate already reports (the user's call, answering the open call raised in the group's run).

**Open calls:** none — all answered 2026-11-07.

**Guardrail(s).** The report is the guardrail: every frame up to the boot's end matches SwanStation's checksums, every test's TTY matches its hardware `psx.log` or differs only where a listed known gap explains it, and any per-instruction divergence from ProjectPSX is either fixed or listed as a known ProjectPSX error with psx-spx's evidence. Hermetic tests in 3e and 3f keep running in `swift test`. Carried from 3f (2026-11-07, when it shipped): the console's per-frame trace for the boot also matches ProjectPSX's frame by frame, its first divergence naming the frame — expected to differ in timing, since 3f's devices run at the real rate where ProjectPSX's run three times faster ([Milestone J](../../assistant/MILESTONES.md#milestone-j--the-ps1-console)).

**Acceptance criteria:**
- [ ] In a personal build with the user's BIOS (the user's run), the BIOS boots to its shell with per-frame guest state matching SwanStation's.
- [ ] ps1-tests' `access-time`, `code-in-io`, `cop` and `io-access-bitwidth` print their hardware `psx.log`, or differ only where a known gap explains it, each difference listed in MILESTONES.
- [ ] Every divergence from ProjectPSX's per-instruction trace is fixed or listed with psx-spx's evidence.
- [ ] Instructions per second for the boot are recorded in MILESTONES (ADR 0015's enforcement from here on).
- [ ] Shipping this item empties v0.0.1's table.

**Scope note.** v0.0.1, track 3, last: gated on 3d (the reference's and the oracle's traces); 3f (the console) shipped 2026-11-07. The runner has what it needs in `PS1Machine`: `boot(_:)` for a PS-EXE after the BIOS, `capturesBIOSPutchar` for the TTY ps1-tests print through the BIOS, and a generic tracer. Known gaps it should expect: psx-spx's access-time formula misses the hardware log for expansion 2, the CD-ROM and the SPU; the CD-ROM, SPU, MDEC and pads are stubs; there is no GTE until v0.2.0, so COP2 raises Coprocessor Unusable; and two of ProjectPSX's behaviours are kept for this comparison to settle — the vertical blank's interrupt at the field's end whatever GP1(07h)'s Y2 holds, and linked-list DMA's 0xFFFF-node guard ([Milestone J](../../assistant/MILESTONES.md#milestone-j--the-ps1-console)). Out of scope: anything drawn on screen (v0.1.0) and games (v0.2.0).
