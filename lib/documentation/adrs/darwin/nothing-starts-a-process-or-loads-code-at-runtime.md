# ADR 0022 — Nothing in the package or the apps starts a process or loads code at runtime

**Status:** Accepted · **Date:** 2026-11-14

## Context

[ADR 0008](emulators-are-separate-programs.md) (2026-10-31) made iStation a launcher, for reasons legal as much as technical: it talked to an emulator only through its command line and its process exit, never by linking, embedding, loading (`dlopen`) or modifying its code, and one module, `InfrastructureProcess`, started processes, reached from Business only through `BusinessLaunching`. Its check failed on `Process(`, `posix_spawn`, `NSTask`, `dlopen(` or `system(` in a source file outside `source/infrastructure/process/` (seen to fail on a planted violation, 2026-10-31). [ADR 0010](cores-are-ports-of-open-references.md) kept the rule and its exemption for the consoles without a native core.

The App Store brief (2026-11-07) replaced that plan. [ADR 0013](shipped-code-derives-only-from-permissive-references.md) superseded ADR 0010 and carried its allow-list and its no-Sony-files rule, but not the process rule: its Enforcement, "unchanged from ADRs 0008 and 0010", lists the check's other parts only. [ADR 0016](two-build-routines-and-a-fresh-start.md) retired the library app, and v0.0.1's item 3b ([Milestone F](../../assistant/darwin/MILESTONES.md#milestone-f--the-skeleton-and-both-build-routines)) removed `InfrastructureProcess`, `BusinessLaunching` and the exemption with it and widened the check to every Swift file of the package's sources and the apps', its `system(` pattern narrowed so `Font.system(size:)` isn't a match; it was seen to fail on a planted `Process()` in an app. Since then the rule has been enforced with no Accepted record: [CLAUDE.md](../../assistant/darwin/CLAUDE.md) carries it as a sub-rule of "⚠ Shipped code comes only from permissive sources", and the Infrastructure layer card and `ProjectRulesTests.swift`'s doc comment attributed it to ADR 0013, which doesn't state it (re-pointed here the same day). Found at v0.0.1's pre-merge docs pass, 2026-11-14.

The rule's first reason — installed emulators, and their licences, kept outside iStation's code — retired with the launcher ([SPEC](../../assistant/darwin/SPEC.md#non-goals): no launching other emulators, the user's call, 2026-11-07). What iStation's records give for it today:

- **The release build's sandbox**: "The App Sandbox the release build needs can't start other emulators and reaches only files the user picks" (ADR 0016's Context). That is the App Store routine's: the personal routine's sandbox is "as needed for the tools" (SPEC), and `lib/src/darwin/apps/macos/Personal.entitlements` carries none.
- **The shipped-code invariant.** CLAUDE.md files the rule under "⚠ Shipped code comes only from permissive sources", whose reason is ADR 0013's: GPL code on the App Store is legally contested, and the project can't grant an exception. A process and `dlopen` are how iStation reaches a GPL emulator today, from tools that never ship: `lib/src/darwin/tools/gate/run.sh` starts the oracle's frontend, which opens SwanStation's libretro core with `dlopen` (`tools/swanstation-oracle/frontend.c`). And the invariant's checks read only what the apps are built from — `noExternalPackages` reads `Package.swift` (a `.package(` off the empty `allowedPackages`, a `.binaryTarget(` or a `.systemLibrary(` fails), and ADR 0014's header checks read the package's and the apps' Swift files: code opened at run time would be in neither.

JIT is asked separately, as whether an app built the App Store way "can generate and run code" ([Milestone E](../../assistant/darwin/MILESTONES.md#milestone-e--jit-under-the-app-store-routine)): the PS2 needs a code generator, so the PS2 is macOS-only. `lib/src/darwin/tools/jit-probe/` showed on 2026-11-07 that an ad-hoc-signed, sandboxed, hardened-runtime macOS app with `com.apple.security.cs.allow-jit` maps a `MAP_JIT` region, writes two AArch64 instructions of its own there and runs them, and that without `allow-jit` the region is refused; runs (2) and (3), signed and through TestFlight, are the user's and still open. iOS App Store apps can't generate code at run time, so the iOS app is interpreter only ([SPEC](../../assistant/darwin/SPEC.md#apple-constraints)).

## Decision

1. **Shipped code starts no process and loads no code at runtime.** Shipped code is the code the apps are built from: the package's sources (`lib/src/darwin/source/`) and the apps' own (`lib/src/darwin/apps/`), in both routines — code under `#if PERSONAL_BUILD` too. No module is exempt; the one that was, `InfrastructureProcess`, is retired. Starting a process is running another program, by `Process` (`NSTask`), `posix_spawn`, C's `system()` or any other means. Loading code is running host machine code that comes from outside the app as it was built — from a file, a download or another program: a library or plug-in opened with `dlopen`, or a bundle loaded at run time.
2. **Code a core generates is not loaded code.** A code generator — the PS2's, on macOS, when it comes — writes the AArch64 instructions it translated from the guest program during the run into a `MAP_JIT` region and runs them, toggling `pthread_jit_write_protect_np` and invalidating the instruction cache, as the JIT probe does. Those instructions are made in memory by the app's own linked code, not read from anywhere: that is generating code, which this rule leaves to the build routines — on macOS under `com.apple.security.cs.allow-jit`, and in the App Store routine never `com.apple.security.cs.allow-unsigned-executable-memory` ([ADR 0016](two-build-routines-and-a-fresh-start.md) §1); on iOS, whose App Store apps can't generate code at run time, the cores interpret ([SPEC](../../assistant/darwin/SPEC.md#apple-constraints)). The BIOS, the games and the PS-EXE programs a console loads into guest memory (`PSEXE`) are guest code, which a core interprets or translates — never host code that the app runs.
3. **The rule binds shipped code alone.** The tools under `lib/src/darwin/tools/` live outside the shipped apps ([CLAUDE.md](../../assistant/darwin/CLAUDE.md)), and today they start processes and load code: `gate/run.sh` runs the Swift console (`istation-run`), ProjectPSX's traced build and SwanStation's oracle, and `swanstation-oracle/frontend.c` opens SwanStation's libretro core with `dlopen`. The package's tests aren't shipped code, and the check doesn't read them: the Infrastructure tests card (`lib/src/darwin/tests/infrastructure/CLAUDE.md`) lists "no processes" among its hermetic conventions, and review holds it.

## Consequences

- A console runs inside the app, as modules of the package linked when the app is built. Running a core out of process — which [ADR 0015](a-core-is-a-cpu-module-and-a-console-module.md)'s narrow interface keeps possible — or adding a helper program, a plug-in or downloaded code would start a process or load code: each needs a record superseding this one, with `nothingSpawnsProcesses` changed in the same change.
- Tools that start another program or open its code — the gate, ProjectPSX's traced build, the oracle — stay under `lib/src/darwin/tools/` and are run from a shell. A personal build's debug UI can't start them: the check reads `#if PERSONAL_BUILD` code too.
- A code generator needs no exception: the check matches none of `mmap`, `MAP_JIT`, `pthread_jit_write_protect_np` or `sys_icache_invalidate`. No code in the package generates code today; `tools/jit-probe/` is the only iStation code that does, and it is not part of any shipped app.

## Enforcement

`ArchitectureTests/ProjectRulesTests.swift`: `nothingSpawnsProcesses` reads every `.swift` file under `lib/src/darwin/source/` and `lib/src/darwin/apps/` (`shippedFiles`) line by line — comments and string literals included, under whatever `#if` — and fails on any line matching `\bProcess\s*\(`, `\bposix_spawn`, `\bNSTask\b`, `\bdlopen\s*\(` or `(?<![.\w])system\s*\(`: the word `Process` followed by `(` (`Foundation.Process(` too; not `ProcessInfo`), any word beginning `posix_spawn`, the word `NSTask` anywhere, the word `dlopen` followed by `(`, and `system` followed by `(` unless a `.` or a word character comes right before it (C's `system()`, not `Font.system(…)`); whitespace may sit before each `(`. Each failure reads `[process in a shipped file] <file>:<line>: <the line, trimmed>`, the file relative to `lib/src/darwin/`. No file under those two folders is exempt, and nothing else is read: not `Package.swift`, `tests/`, `tools/` or `scripts/`, nor a file that isn't Swift. Seen to fail on a planted `Process()` in an app, 2026-11-07 ([Milestone F](../../assistant/darwin/MILESTONES.md#milestone-f--the-skeleton-and-both-build-routines)).

The check is narrower than §1: it doesn't match `Process.run(…)` or `Process.init()`, `Darwin.system(…)`, `fork` or the `exec` family, `popen`, launching an app through Launch Services (`NSWorkspace`), starting an XPC service, or `Bundle.load()`; review holds those. §2 is half checked: `appStoreEntitlementsAreClean` ([ADR 0016](two-build-routines-and-a-fresh-start.md)) fails on `com.apple.security.cs.allow-unsigned-executable-memory`, `com.apple.security.get-task-allow` or `<key>get-task-allow</key>` in any `AppStore.entitlements` in the repository (outside `.git`, `.build`, `.swiftpm`, `build`, `DerivedData` and `worktrees` folders), when there is no `AppStore.entitlements` at all, and on a folder under `lib/src/darwin/apps/` other than `Config` without both `AppStore.entitlements` and `Personal.entitlements`. That executable memory comes only from a `MAP_JIT` region a core's own generator writes has no check; review holds it.
