# The Business layer

**Position.** Third of the four ([ADR 0024](../../../../documentation/adrs/darwin/four-layers-and-business-holds-the-session.md)): the cores — what a console does — and `session`, what the apps do with a core, which is not a core itself. Today the R3000A interpreter and the PS1 console, both ported from ProjectPSX: the console's memory map, interrupts, timers, DMA and GPU timing, with the other devices stubbed until their versions; and iStation's own session, which runs the PS1 console off the main actor for the player.

**Modules:** `r3000a` (the R3000A interpreter: the PS1's CPU and the PS2's I/O processor), `ps1` (the PS1 console: memory map, devices, the run loop, PS-EXE loading), `session` (the console session: one console run off the main actor, 60 frames a second by a clock, with power on, pause, resume, reset, stop and a snapshot stream; in personal builds the tracing console, counting instructions)

**May depend on:** Business, Data and Infrastructure — and no UI or Apple framework: the Swift standard library (Swift concurrency included, for `session`), and nothing else without a recorded reason ([ADR 0015](../../../../documentation/adrs/darwin/a-core-is-a-cpu-module-and-a-console-module.md)). A CPU family is one module generic over its bus; a console is one module owning its memory map; hot paths use concrete types or `@inlinable` generics, never protocol-typed values, and a class's stored `var`s on a hot path are `@exclusivity(unchecked)` (the dynamic check cost the R3000A 15×). Shipped code comes only from permissive sources, with its notice ([ADR 0013](../../../../documentation/adrs/darwin/shipped-code-derives-only-from-permissive-references.md), [ADR 0014](../../../../documentation/adrs/darwin/own-code-is-mit-and-derived-code-keeps-its-notice.md)).

**Enforced by:** one SwiftPM target per module, generated from the module map in `lib/src/darwin/Package.swift`, and `ArchitectureTests` (`lib/src/darwin/tests/architecture/`), run by `swift test`.

**Changing this layer:**
- A new module: its directory `source/business/<module>/`, its `Module(.business, "<Name>", uses: […])` row in `Package.swift`, its tests in `tests/business/<module>/` (and in the `macOS Personal` scheme of `lib/src/darwin/iStation.xcodeproj`), its name on this card and in [ADR 0002](../../../../documentation/adrs/darwin/module-map.md)'s table — in the same change.
- A core reaches TraceKit only through a generic tracer a release build specializes to nothing, its imports under `#if PERSONAL_BUILD` ([ADR 0016](../../../../documentation/adrs/darwin/two-build-routines-and-a-fresh-start.md)).
- The apps run a console through `session`, never by calling `runFrame()` themselves: the console is the `ConsoleSession` actor's own state, so it is driven from one place, between frames ([ADR 0015](../../../../documentation/adrs/darwin/a-core-is-a-cpu-module-and-a-console-module.md) §4); the player reaches it through `ConsoleSessionControls`, which a fake stands in for in its previews and tests.
